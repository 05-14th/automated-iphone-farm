The sender identity is an iMessage-enabled Apple Account *email*, not a cellular number. ## 1. The two defects this model exists to absorb

Both are measured, not theoretical. See `docs/PHASE1-REPORT.md`.

### Defect A — the API reports failure on a send that succeeded

`POST /api/v1/message/text` and `/api/v1/chat/new` return **HTTP 500 or time out at 30 s while the message is in fact delivered** (`error=0`, present in provider state). The server's await/reconcile step gives up before AppleScript settles; `chat/new` additionally throws `-1728 Can't get chat id` *after* creating the chat.

There is a second, independent reason the HTTP response is not truth: a send issued while the Mac is offline still returns **HTTP 200** and is delivered minutes later, once the link returns [18]. So `2xx` does not mean delivered, and `5xx`/timeout does not mean failed. **The HTTP response carries no reliable information about delivery in either direction.**

A naive worker that trusts the response and retries *will* double-send.

How the schema absorbs it:

| Mechanism | Role |
|---|---|
| `messages.temp_guid` + `messages_temp_guid_uidx` | The reconciliation key. Generated by the worker and written **before** the HTTP call, echoed back by BlueBubbles as `tempGuid`. After an ambiguous response, the message is located in provider state by this value. Unique, so that lookup resolves to exactly one row. |
| `messages_outbound_temp_guid_chk` | An outbound message with no `temp_guid` is unrepresentable. Without it, a timeout would leave nothing to reconcile against. |
| `messages.reconciled` | True once the row has been checked against provider state after an ambiguous outcome. |
| `trg_messages_state_machine` | `failed → queued` and `failed → sent` both **require `reconciled = true`**. This is the enforcement point: the database refuses to let a message be retried before it has been reconciled. |
| `send_attempts` | One row per HTTP call, whatever the outcome. The audit trail that makes the defect debuggable after the fact. |
| `messages_unreconciled_failed_idx` | Partial index over `state = 'failed' AND reconciled = false` — the triage queue. This set must be empty before any retry sweep is considered safe. |
| `can_send()` in-flight check | Nothing new goes out on a conversation while a send of unknown outcome is still open on it. |

The rule, stated once: **never retry on a timeout or 5xx without first reconciling against provider state.**

### Defect B — duplicate outbound echo webhooks with an identical GUID

BlueBubbles dispatches the same `new-message` event twice, ~1 ms apart, carrying an **identical** provider GUID. Verified server-side with a single BlueBubbles process and a single registered webhook.

Measured rate: **8 of 11 outbound sends duplicated; 7 of 7 successful `POST /api/v1/message/text` calls into an existing chat duplicated.** The three that did not were a native Messages send, a send that returned 500 (Defect A), and a `chat/new` send. The trigger is a *successful* `message/text` send — precisely the bridge's hot path. Inbound did not duplicate (0 of 2), but is treated as at-least-once anyway [35].

How the schema absorbs it:

```sql
create unique index messages_provider_guid_uidx on public.messages(provider_guid) where provider_guid is not null;
```

Verbatim from guide step 31. Every ingest path writes with `ON CONFLICT (provider_guid) DO NOTHING` (or `DO UPDATE` for delivery-receipt enrichment), and the second copy of the event collapses into the first. This is not optional hardening; at a measured 73% duplication rate on the hot path it is the difference between a working bridge and one that double-writes most of its traffic.

Note the index is **partial** (`where provider_guid is not null`). A queued outbound message has no provider GUID yet, and many rows sit in that state simultaneously; a full unique index would collide on NULLs in some engines and adds nothing here.

## 2. Tables

### `senders` [31, 32]
One row per iMessage sender identity, `sender01`…`sender05` (`slug` is regex-constrained to that range). Each has its own Apple Account email, its own BlueBubbles URL/port (`12341`, `12342`, …), and its own macOS Standard user (`imsg01`, …).

`status` is `active | paused | failed`. **Only `active` senders send.** `senders_paused_reason_chk` forces a `paused_reason` whenever status leaves `active`, because the operator alert needs to say why.

### `contacts` [31, 32]
One row per recipient identity. `normalized_address` is the canonical key used by *every* suppression and routing check; `raw_address` preserves whatever the operator or import supplied. `contacts_normalized_address_uidx` guarantees one row per real-world address.

`sticky_sender_id` is `NOT NULL` and **immutable** — see §4.

### `conversations` [31, 34, 35]
The `(contact, sender)` thread, unique on that pair. FIFO is scoped here.

`provider_chat_guid` is **nullable** and unique-when-present. Nullable because `chat/new` can create the chat and still throw `-1728 Can't get chat id` (Defect A) — a null GUID never means "no chat exists on the provider". Unique-when-present so a reconciliation pass cannot attach one provider chat to two rows.

### `messages` [31, 33, 34, 35]
Both directions. Carries the send state machine (§5) and both defect mechanisms.

`messages_inbound_shape_chk` encodes that inbound messages are observed facts: they arrive already `sent`, already carrying a `provider_guid`, and never have a `temp_guid` — we did not queue them.

Note `sent_at` vs `delivered_at`: **acceptance is not delivery.** `sent_at` is when the provider accepted; `delivered_at` is the confirmed `error=0` echo. On the offline-send path these can be minutes apart.

### `consents` [31, 36]
**Append-only ledger.** Rows are never mutated; a revocation is a *new* row with `status = 'revoked'`. The current verdict is the newest row per contact, which is what `can_send()` reads. `evidence` (jsonb) holds the proof — form payload, IP, timestamp, recording reference.

This table records what happened. It does not decide what is lawful: qualified counsel must validate the exact consent, identification and unsubscribe requirements for every jurisdiction contacted [36].

### `suppressions` [31, 36]
Keyed on `normalized_address`, unique, and **global across every sender and every conversation**. There is deliberately **no `sender_id` column**: someone who said STOP to `sender01` has said STOP to the operator, and must not be reachable from `sender03`. Suppression is the first check in `can_send()` and outranks consent.

`reason` is `stop | dnc | bounce | manual`.

### `send_attempts` [33]
The Defect A audit trail. One row per HTTP call to BlueBubbles, with `http_status`, the raw `response` jsonb, and an `outcome` of:

| outcome | meaning |
|---|---|
| `accepted` | 2xx from the provider. **Still not proof of delivery.** |
| `timeout` | No response within 30 s. Message status genuinely **unknown**. |
| `error` | Explicit provider failure. |
| `reconciled_sent` | A later provider-state lookup by `temp_guid` proved this ambiguous attempt actually delivered. |

Read the attempt history as a story. `timeout → reconciled_sent` is a correctly handled false failure. `timeout → accepted` is a **double-send** and a pilot-gate violation — guide step 38 tracks "duplicate sends" and "unreconciled timeouts" explicitly. `http_status = 500` here does not imply the message failed; the measured defect is precisely that it usually delivered.

`attempt_no` is monotonic per message and unique on `(message_id, attempt_no)`.

## 3. FIFO rule [34]

> Messages within a conversation must be sent in order, while unrelated conversations may progress independently.

Three mechanisms, in increasing strength:

1. `messages_conversation_created_idx` on `(conversation_id, created_at)` — the ordering scan the worker claims from.
2. `messages_one_sending_per_conversation_uidx` — a **unique index on `conversation_id` where `state = 'sending'`**. At most one in-flight send per conversation, enforced by the database rather than by worker etiquette. Two workers racing for the head of the same queue: one wins, the other gets a unique violation and backs off.
3. `can_send()` returns `in_flight_message_exists` while anything is `queued` or `sending` on the conversation.

Parallelism is across conversations and across senders, never within a conversation. `messages_queued_outbound_idx` (`sender_id, queued_at` where queued+outbound) is the per-sender claim path.

The FIFO rule doubles as a Defect A containment: while a send whose outcome is unknown sits open on a thread, nothing else may go out on that thread and compound the ambiguity.

## 4. Sticky routing rule [32]

> A contact stays pinned to its first sender identity. Never silently reroute to another sender when the assigned sender fails; pause the sender and alert instead.

A contact's `sticky_sender_id` is set on first contact and **never changes**. Rerouting is the tempting fix when a sender goes down, and it is exactly the wrong one: the recipient would see their conversation continue from a stranger's email address. That is the single worst trust failure available in this channel.

Four layers enforce it:

| Layer | Enforcement |
|---|---|
| `contacts.sticky_sender_id NOT NULL` | Every contact is pinned from the moment it exists. |
| `trg_contacts_sticky_sender_immutable` | Hard-raises on any attempt to change it. |
| `trg_conversations_sender_must_be_sticky` | A conversation's `sender_id` must equal the contact's sticky sender. |
| `trg_messages_sender_must_match_conversation` | A message's `sender_id` must equal its conversation's. |
| `conversations_contact_sender_uniq` | Makes a second, wrong-sender thread unrepresentable. |

When a sender fails, the correct behaviour is: set `status = 'paused'` (or `'failed'`) with a `paused_reason`, alert, and **stop**. `can_send()` then returns `sender_paused:sender01` for every contact pinned to it. Those contacts do not receive messages until the sender is fixed. That is the intended outcome, not a bug to route around.

Operational note carried over from Phase 1 [21]: a Mac reboot leaves the sender offline until a human logs into its macOS user, because no auto-login is configured. That outage is invisible to this schema — the sender row still reads `active` while its BlueBubbles instance is dead. A health check must flip `status` to `paused`; otherwise the worker queues into a void. Enabling auto-login for `imsg01`, or a boot-time alert, remains an open Phase 1 item.

## 5. The state machine [33]

```
                      ┌──────────────────────────────┐
                      │                              │
                      ▼                              │ reconciled = true
   (insert) ──▶ queued ──▶ sending ──▶ sent          │ (proven NOT delivered)
                  │           │                      │
                  │           └──────▶ failed ───────┘
                  └──────────────────▶   │
                                         │ reconciled = true
                                         └──────────▶ sent
                                            (proven delivered — Defect A recovery)
```

Enforced by `trg_messages_state_machine`. Legal transitions:

| From | To | Condition |
|---|---|---|
| `queued` | `sending` | worker claims it |
| `queued` | `failed` | pre-flight rejection |
| `sending` | `sent` | provider accepted **and** the echo/provider state confirms |
| `sending` | `failed` | explicit error, **or** timeout (status unknown — see below) |
| `failed` | `queued` | **only with `reconciled = true`** — reconciliation proved it did *not* deliver, so a retry is safe |
| `failed` | `sent` | **only with `reconciled = true`** — reconciliation proved it *did* deliver. This is the Defect A recovery edge. |

`sent` is **terminal**. Any other transition raises.

Timestamps `sending_at` / `sent_at` / `failed_at` are auto-stamped by the trigger if the caller leaves them null. `queued_at` is re-stamped on requeue.

Inbound messages are inserted directly as `sent` and never traverse the machine.

### Worker sequence for an ambiguous outcome (Defect A)

1. Generate `temp_guid`, insert the message as `queued`.
2. `queued → sending`; insert `send_attempts` row `attempt_no = 1` once the HTTP call returns.
3. Response is a timeout or 5xx → record `outcome = 'timeout' | 'error'`, move `sending → failed` with `reconciled = false`. **Stop. Do not retry.**
4. Reconciliation pass reads `messages_unreconciled_failed_idx`, queries BlueBubbles provider state by `temp_guid` (or text + chat + time window as a fallback).
   - **Found** → `failed → sent` with `reconciled = true` and the real `provider_guid`; append `send_attempts` row with `outcome = 'reconciled_sent'`.
   - **Not found** → `failed → queued` with `reconciled = true`. Only now may `attempt_no = 2` happen.

Step 3 to step 4 is the whole mitigation. The database will not let step 4 be skipped.

## 6. `normalize_address(text)` [31]

> Normalize recipient identifiers before suppression/routing checks.

```
'  MeIdY@ClarioCapital.COM '  →  'meidy@clariocapital.com'
'(778) 323-1234'              →  '+17783231234'
'+1 778-323-1234'             →  '+17783231234'
'17783231234'                 →  '+17783231234'
```

Rules: if the value contains `@` it is an email — lowercase and trim. Otherwise strip everything that is not a digit and render E.164; a leading `+` means the digits are already international, a bare 10-digit value is assumed NANP and gets `+1`, an 11-digit value starting `1` gets `+`. `IMMUTABLE`, so it could back a functional index if that is ever wanted.

Applied automatically by `BEFORE INSERT OR UPDATE` triggers on **`contacts`** (`trg_contacts_normalize_address`) and **`suppressions`** (`trg_suppressions_normalize_address`). Callers may supply only `raw_address`; the trigger derives the normalized form.

This is what makes suppression actually work: a STOP recorded as `(778) 323-1234` suppresses a contact stored as `+17783231234`, and a STOP recorded as `MEIDY765@Gmail.com` suppresses `meidy765@gmail.com`. A suppression list compared against un-normalized input is a suppression list that silently leaks.

## 7. `can_send(p_contact_id uuid) → jsonb` [36]

The single pre-send gate. Returns `{"allowed": bool, "reason": text}` and returns on the **first** failure, in this fixed order:

| # | Check | Reason on failure |
|---|---|---|
| 0 | contact exists | `contact_not_found` |
| 1 | **suppression** — global, all senders | `suppressed:stop` / `suppressed:dnc` / … |
| 2 | **valid consent** — newest ledger row must be `granted` with an effective `granted_at` | `no_consent_on_record`, `consent_revoked`, `consent_not_yet_effective` |
| 3 | **sender paused** — sticky sender must be `active` | `sender_paused:sender01`, `sender_failed:sender03`, `sticky_sender_missing` |
| 4 | **sticky-sender match** — an existing conversation must belong to the contact's sticky sender | `sticky_sender_mismatch` |
| 5 | **in-flight message** — FIFO + Defect A containment | `in_flight_message_exists` |
| — | all clear | `allowed: true, reason: "ok"` |

Success: `{"allowed": true, "reason": "ok"}`.

**The order is load-bearing.** A suppressed contact must never be evaluated for consent — otherwise a later opt-in record quietly reopens a channel someone asked to leave. And a paused sender must never be evaluated for an alternative; there is no alternative by design (§4).

`SECURITY DEFINER` with a pinned `search_path`, so the worker gets a truthful verdict regardless of the caller's RLS view. It is revoked from `public`, `anon` and `authenticated`. It takes only a contact id — **never widen it to accept a sender override**, since that parameter would be the exact hole through which sticky routing gets bypassed.

Operating caps and quiet hours [36] are policy, not schema, and are not implemented here. They belong in the worker on top of this verdict.

## 8. RLS

Every one of the seven tables has RLS **enabled** and one explicit **deny-all** policy (`using (false) with check (false)` for `public`).

**Service-role bypass:** Supabase's `service_role` is created with the `BYPASSRLS` attribute and is therefore not subject to any policy here. The bridge worker and the webhook ingest run as `service_role` and keep full access *without any policy being written for them*. That is deliberate — the only way to reach this data is the trusted server-side worker.

The deny-all policy is technically redundant with "RLS on, no policies". It is written out anyway so that a future `create policy` cannot widen access simply by being the only policy on the table; a reviewer sees the explicit deny sitting next to it. Table-level grants are also revoked from `anon` and `authenticated` as a second line.

**No auth roles are invented.** The portal reads through the worker [35], not by handing browsers a key. If portal users ever need direct read access, that is a separate, reviewed migration.
